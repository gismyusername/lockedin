## Problem Statement

A Mac app that passively logs how much you actually work — no daily activation, no start/stop buttons — and turns it into a shared scoreboard with friends. The competition and live peer pressure are the point; the tracking is just the input.

## What Makes This Cool

- **Live presence is the "whoa"**: the menu bar shows which friends are locked in *right now*. Seeing "Marc — grinding now" at 11pm makes you open your editor. It creates spontaneous co-working, not just retrospective stats.
- **The score is honest**: "locked in" = your hands are actually on the keyboard/mouse. No gaming it by leaving YouTube open.
- **Zero-permission tracking**: macOS exposes global idle time (`CGEventSourceSecondsSinceLastEventType`) without Accessibility, Input Monitoring, or Screen Recording prompts. Install → it just works. Every incumbent (Rize, Timing) builds app-categorization engines; choosing active-input time as the score makes that entire problem disappear.
- **Set-and-forget**: launches at login, lives in the menu bar, never asks for anything.

## Constraints

- macOS 13 Ventura or later (`MenuBarExtra` and `SMAppService` require it) — confirm friends' Macs qualify. Apple Silicon + Intel via universal binary.
- Fun side project: ship to friends in a weekend, not a month.
- Builder has a web-dev background (TypeScript/Next.js/Supabase); Swift is new but Claude Code writes it.
- Privacy hard line: only display name, locked-in seconds, and online status ever leave the Mac. No app names, no window titles, no screenshots.
- Free-tier infrastructure only (Supabase free plan).

## Premises (agreed)

1. Score = active input time: user is "locked in" when the last global input event was < 60s ago. Accumulated in 5s polling ticks.
2. Menu bar app, launches at login via `SMAppService`, no daily activation.
3. Friends join a group via invite code; each Mac heartbeats (~1/min) to a shared backend; Supabase Realtime broadcasts presence back.
4. Only display name + locked-in seconds + live status leave the machine.
5. Distribution via GitHub Releases, unsigned in v1. Note: on macOS 15+ the old right-click → Open bypass is gone — friends must use System Settings → Privacy & Security → "Open Anyway" (or `xattr -d com.apple.quarantine`). Notarization ($99/yr Apple Developer) deferred, but this friction is the first thing to fix if it annoys people.

## Approaches Considered

### Approach A: Native Swift + Supabase (CHOSEN)
- Summary: SwiftUI `MenuBarExtra` app polls system idle time every 5s, accumulates locked-in seconds locally, heartbeats Supabase every 60s; Supabase Realtime pushes friends' presence back. Invite code = group row.
- Effort: S (human: ~1 week / CC: ~2–3 hours) · Risk: Low
- Pros: ~500 lines, fully native feel, near-zero RAM, no server code (Supabase Realtime gives live presence for free), builder already knows Supabase.
- Cons: Swift/Xcode unfamiliar to the builder.
- Reuses: builder's existing Supabase experience (Polywin uses it).

### Approach B: Tauri tray app on the web stack
- Summary: Tauri v2 tray app — Rust core reads idle time, React/TypeScript UI, same Supabase backend.
- Effort: M (human: ~1–2 weeks / CC: ~3–4 hours) · Risk: Medium
- Pros: UI in the stack the builder uses daily; cross-platform later.
- Cons: heavier binary and toolchain for a tiny app; tray idle-detection less battle-tested than one Swift API call.

### Approach C: Full native product
- Summary: Approach A plus desktop widget, weekly recap notifications, Sparkle auto-updates, notarized installer.
- Effort: L (human: ~1 month / CC: ~1–2 days) · Risk: Medium
- Cons: weeks of polish before any friend sees a leaderboard — momentum killer. Kept as the V2 direction.

## Recommended Approach

**Approach A.** Architecture:

```
┌─ Mac (per friend) ──────────────────────────┐
│ MenuBarExtra (SwiftUI)                      │
│  ├─ IdleTracker: every 5s read              │
│  │   CGEventSourceSecondsSinceLastEventType │
│  │   idle < 60s → add 5s to today's total   │
│  ├─ LocalStore: daily totals in             │
│  │   UserDefaults, day rolls over at local  │
│  │   midnight                               │
│  └─ SyncClient: every 60s upsert            │
│      {user_id, date, seconds, is_active,    │
│       last_active_at, heartbeat_at: now()}  │
└──────────────┬──────────────────────────────┘
               ▼
        Supabase (free tier)
        tables: users, groups, memberships, daily_scores
        Realtime: daily_scores changes → all group members
        RLS: score writes restricted to the row's owner (see Open Questions)
```

- **UI** (wireframe approved, screenshot at `/private/tmp/claude-501/-Users-g-Desktop-GitHub/72380fe3-666b-404a-98cc-a592ad8e80d5/scratchpad/lockedin-sketch.png`; copy into the repo as `docs/wireframe.png` when the project is scaffolded):
  - Menu bar item: `● 4:12 | 2 grinding` (live timer + active-friend count).
  - Popover: big monospaced daily timer + LOCKED IN / idle pill → "Live" friend rows (green pulsing dot, "grinding now" / "idle 23m") → "Today" leaderboard with proportional bars, crown on #1, current user highlighted → footer with streak flame + settings.
  - Empty state: timer + one "Invite friends — share code XKCD-42" button.
  - Edge cases: long names truncate; 0m day shows "0m — lock in?"; offline Macs show "last seen 2h ago".
- **Identity**: no accounts. First launch generates a UUID + asks for a display name. (Acceptable trust model for friends; see Open Questions for the cheating caveat.)
- **Groups**: first launch offers "Create group" (generates a 6-char invite code, stores a `groups` row) or "Join group" (enter a code). v1 supports exactly one group per install; the `memberships` join table exists so multi-group can be added later without a migration.
- **Presence rules** (derived client-side from `last_active_at` and `heartbeat_at`; exhaustive — every row matches exactly one state):
  - `is_active` = idle < 60s at heartbeat send time.
  - "grinding now" = `is_active` AND `heartbeat_at` < 2 min old — a crashed or offline Mac drops off the live list within 2 minutes.
  - "idle Nm" = `heartbeat_at` < 10 min old AND not grinding (covers both not-active and active-but-stale-2-to-10-min, e.g. lid closed mid-grind); N = minutes since `last_active_at`.
  - "last seen Xh ago" = `heartbeat_at` ≥ 10 min old.
- **Streak** (v1, cheap and fun): consecutive user-local days with ≥ 30 min locked in, computed client-side from `daily_scores`. No server logic.
- **Offline**: seconds accumulate locally regardless; sync catches up when online.

## Open Questions

1. **Cheating**: a mouse jiggler (or `caffeinate`-style script) defeats active-input scoring. Accepted for v1 — it's friends; shame is the anti-cheat. Revisit only if it actually happens.
2. **RLS without real auth**: with anonymous UUID identity, Supabase anon-key writes can technically spoof another user's row. v1 accepts this (friends-only); the clean fix is Supabase anonymous auth (built-in) so each install gets a real JWT and RLS enforces `user_id = auth.uid()`.
3. **Timezones**: friends in different timezones have different "today". v1: each user's day is their local day; leaderboard groups by each user's own local date. Good enough for a friend group in the same country.
4. **Laptop asleep / lid closed**: no ticks accumulate (timer only counts awake, active input) — correct by construction, but verify after sleep/wake that the day rollover logic didn't skip.

## Success Criteria

- Install → menu bar timer counts up within 60 seconds, zero permission prompts.
- Two Macs in the same group see each other's "grinding now" status within ~2 minutes.
- Survives reboot with no user action (launch-at-login works).
- At least 2 friends install it and check the board unprompted in week one.
- App uses < 50 MB RAM and doesn't show up in battery complaints.
